# XHS_260731175346 小红书云端限制绕过分析

> 版本：XHS_260731175346.apk
> 目的：分析 XHS 模块对**小红书自身云端**的消息撤回与媒体限制的绕过机制，以及该机制的攻击面与边界。本文是安全研究与逆向学习用途的机制分析。
> 前置阅读：[XHS_260731175346-云端信息调用逻辑.md](XHS_260731175346-云端信息调用逻辑.md)

---

## 一、信任模型

XHS 与 DY Helper 的授权模型**完全不同**：

- DY Helper：自建"作者云端"（GitHub 名单 + native 校验），破解目标是**作者的授权服务器**。
- XHS：**不信任小红书云端**。它没有自建服务器，而是 Hook 小红书客户端内部方法，直接改写客户端与云端之间的数据流。

```
小红书云端
   │  ① 长连接推送服务端消息（含撤回指令 getServerRevokeMsg）
   │  ② HTTP 返回笔记对象 note（图片/视频/音频/保存配置）
   ▼
小红书客户端（com.xingin.xhs / :longlinkNew）
   │  ← XHS 模块在此 Hook（libnative.so）
   │  ① 拦截撤回指令 → 撤回不生效（防撤回）
   │  ② 提取 note 媒体 URL → 去水印 / 解锁保存 / 下载
   ▼
用户获得：撤回的消息仍在、无水印原图原视频、可自由保存
```

模块的运行前提：

1. 被 hook 的是小红书客户端自身进程，网络连接与鉴权均由客户端完成。
2. 模块在目标进程内运行（LSPosed 注入），拥有目标应用的全部内存权限。
3. 核心 hook 逻辑在 `libnative.so`，Java 层只暴露桥接。

**破解本质**：在小红书客户端与云端的交互边界上拦截/篡改数据，让"撤回"与"媒体保护"两种云端能力失效。

## 二、攻击面枚举

| # | 攻击面 | 位置 | 描述 |
| --- | --- | --- | --- |
| 1 | 撤回指令处理 | 长连接进程 hook `getServerRevokeMsg` | 云端下发撤回消息时，模块在目标方法上拦截，阻止撤回生效 |
| 2 | 消息存取 | hook `getMessageDaoMethod` / `getMessageByIdMethod` | 拦截消息 DAO 与按 ID 查询，保证撤回后消息仍可读取 |
| 3 | 媒体保存配置 | `note.mediaSaveConfig.disableSaveMedia / disableWaterMark` | 模块将两开关写为 `false`，解锁保存并去水印 |
| 4 | 媒体 URL 提取 | `note.soundInfo.url` / `videoInfo.url` / `imageInfo.imagesList[].original` / `noteMusicData.audioUrl` | 从云端返回对象中直接取原始媒体地址 |
| 5 | 本地缓存 | MMKV（`dataDir/config`）：`redId`、`nickname`、防撤回状态 | 进程间（主/长连接）共享状态，可被篡改 |
| 6 | Hook 框架边界 | `ModuleMain.hook(executable).intercept()` | LibXposed Hook 目标由 native 决定，可被二次 Hook |
| 7 | native 实现 | `libnative.so`（`C1076.mo213` / `C1144.mo213`） | hook 目标与具体篡改逻辑全部在此，是最终裁决点 |

## 三、绕过路径分析（研究思路）

### 路径 A：Hook 撤回指令处理（防撤回的直接实现）

模块已在长连接进程完成该路径：

1. `C1076.f3467` 声明三个目标方法名；native 层用 DexKit 在目标 DEX 中定位。
2. 对 `getServerRevokeMsg` 所在方法安装 `hookBefore`：**调用前吞掉参数或置空返回，使云端撤回指令不生效**。
3. 对 `getMessageDaoMethod` / `getMessageByIdMethod` 安装 hook，确保撤回后消息仍能从本地 DAO 读出。

> 判定依据：`C0011` 仅在 `com.xingin.xhs:longlinkNew` 进程内初始化防撤回（日志 `防撤回已加载到长连接进程`），说明撤回消息走长连接通道；`C1144.m1844` native 定位具体处理 `Method`。

### 路径 B：篡改媒体保存配置（去水印 / 解锁保存）

模块在笔记详情返回后篡改云端下发的配置对象：

1. `C0911.m1471` 从 `note` 对象取 `mediaSaveConfig`。
2. 将 `disableWaterMark` 置 `true`、`disableSaveMedia` 置 `false`（`C1085.m1749` 写回）。
3. 从 `soundInfo.url` / `videoInfo.url` / `imageInfo.imagesList[].original` / `noteMusicData.audioUrl` 取原始媒体地址。
4. 弹窗提供下载（`C1027` OkHttp 保存到文件）。

> 若需"主动破解"而非等模块触发：直接 hook `note` 对象的 `get`/字段读取，强制返回去水印 URL；或 hook 图片加载路径（`C0911.m1468`、`m1472` 为 native 图片加载桥）。

### 路径 C：篡改本地 MMKV 状态

- MMKV 存于 `dataDir/config`，两个实例分别经 `C0210.m475()` / `m476()` 访问。
- 主进程与长连接进程经 MMKV 共享 `redId`、`nickname`、方法名缓存与防撤回状态。
- 若某功能以上下文状态判断（如"当前账号 / 版本校验"），可直接写 MMKV 键值强制置为已启用。

> 注意：多数关键判断在 native 层完成，改 MMKV 只影响 Java 层状态，能否生效需结合 native 判定。

### 路径 D：逆向 libnative.so 还原 hook 目标

若需完整还原模块"破解"逻辑（而不仅是使用模块）：

1. 用 Ghidra / IDA 打开 `lib/arm64-v8a/libnative.so`，定位导出 `Java_..._xhss_C1076_mo213`、`Java_..._C1144_mo213` 及 `C0911_*` 系列。
2. 还原 DexKit 查找逻辑：确认 `getServerRevokeMsg` 之外还有哪些目标方法（如点赞/收藏/评论撤回、会话删除等）。
3. 还原对 `note.mediaSaveConfig` 的写回与媒体 URL 提取分支。
4. 还原 native 字符串池（对应 Java 侧 `m1313(long)`，native 侧为 `C0911.m1473/m1478(long)`），得到完整业务常量。

### 路径 E：Hook 模块自身（二次 Hook）

- 模块用 LibXposed 的 `HookBuilder.intercept()` 安装 hook，Java 层桥接类（`AbstractC1008`、`C0911`、`C0011`）仍可被二次 hook。
- 可强制 `C1085` 全局状态、或注入假的 `note` 对象以触发模块下载逻辑。
- native 有运行时完整性/反 hook 的可能，需先绕过（`libnative.so` 中未见明文反调试标记，需动态确认）。

## 四、结论

- **与 DY Helper 的本质差异**：XHS 没有"作者云端授权"可破解，它本身就是破解小红书云端限制的客户端工具。因此本分析的"破解云端"指**小红书云端的两类限制**——消息撤回与媒体保护。
- **最脆弱的边界是长连接消息处理**（路径 A）：防撤回完全依赖 `getServerRevokeMsg` 等方法的 hook 生效，Hook 被绕过则撤回恢复。
- **媒体侧是配置篡改**（路径 B）：`disableWaterMark / disableSaveMedia` 两个布尔字段决定了水印与保存限制，模块在笔记对象上直接改写。
- **真正决定权在 native**（路径 D）：Java 层只暴露目标方法名与桥接，最终 hook 目标、篡改分支与字符串常量都在 `libnative.so`。要"理解并复现"该破解，必须对 `libnative.so` 做二进制分析；这也意味着**小红书的对抗重点是检测/阻止该 native Hook**，而不是模块自身的云端。
- 模块自身上限由 LibXposed 框架与目标应用版本决定：小红书版本升级导致方法签名变化时，DexKit 查找失败会使相应功能静默失效。
