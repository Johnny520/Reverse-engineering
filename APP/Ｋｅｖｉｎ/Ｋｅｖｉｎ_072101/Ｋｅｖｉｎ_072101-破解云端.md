# Kevin_072101 破解云端（云端验证机制解构与安全评估）

> 本文从**逆向分析 / 安全研究**角度解构 `kevin.fun` 的"云端"（激活验证后台 + VIP 白名单服务），说明它的架构、协议、授权模型与安全边界。
> 目的：理解该机制**为什么是这样设计**、**强度在哪里**、**弱点在哪里**。本文**不提供**任何绕过付费、伪造授权、生成激活码或篡改包体的可执行步骤。
> 素材：`Ｋｅｖｉｎ_072101-restored-sources` + `kevin-decode-report.tsv` + `Ｋｅｖｉｎ_072101-apktool-full/smali`。

## 1. "云端"是什么

模块的云端服务由作者自己运维，全部面向**授权/会员体系**：

| 组件 | 端点 | 形态 |
|---|---|---|
| 激活验证 | `https://tg-verify-api.kevin0529422.workers.dev/activate` | Cloudflare Workers 边缘函数（serverless） |
| VIP 白名单 | `https://111.kevin42.dpdns.org/vip_list.json` | 自建域名上的静态 JSON 名单 |
| 客服/售卖 | `https://t.me/Kevin_Dyy` | Telegram 群 |

一句话：**云端的唯一职责是"验证激活码并下发授权状态"**。它不承载业务数据，不存储用户内容，只维护"哪些激活码有效、绑定哪个抖音 uid、哪些 uid 是 VIP"。

## 2. 架构拓扑

```
┌─ 客户端（Xposed 模块，运行在抖音进程内）────────────┐
│  DYHook → PPHook  ── POST /activate ──────────────►│
│      │              { activation_code, uid }       │  Cloudflare Workers
│      │                                             │   · 校验激活码有效性
│      └── GET /vip_list.json ◄── JSON uid 名单 ──────│   · 记录 激活码↔uid 绑定
│                                                     │
│  MMKV(kevin_prefs)                                  │  自建域名
│   activation_activated / activation_code            │   · 静态 vip_list.json
│   activation_uid / activated_accounts               │
└─────────────────────────────────────────────────────┘
```

关键点：**激活有效性由服务端判定**（Cloudflare Workers 后端），客户端只负责提交激活码并接受结果。VIP 名单也由服务端下发，客户端只是缓存读取。

## 3. 验证协议

请求（POST `/activate`）：

- Body：JSON `{ "activation_code": "...", "uid": "..." }`
- `User-Agent: Mozilla/5.0 (Android) KevinHook/1.0`
- 走 HTTPS；Java 层未发现自定义签名/加密（见 [Ｋｅｖｉｎ_072101-云端与加密分析.md](Ｋｅｖｉｎ_072101-云端与加密分析.md)）

响应（JSON，反序列化到 `PPHook$ActivateResult`）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `status` | string | `"ok"`（成功）/ `"already"`（已激活）/ 其它（失败） |
| `count` | int | 通常为剩余次数/天数等信息 |
| `error` | string | 失败原因文案 |
| `ok` | bool | 便捷布尔位 |

客户端行为：

- `status == "ok"` → 本地落盘激活状态，弹 VIP 欢迎
- `status == "already"` → 提示已激活
- 其它 → 弹"激活失败：\<error\>"
- 失败重试数轮，日志含 `activateCode attempt=` / `activateCode 第 N 次异常`

## 4. 授权模型

1. **激活码绑定账号**：提交时携带 `uid`，服务端把激活码与抖音 uid 绑定（客户端文案也明示"激活码将绑定此账号"）。
2. **账号级授权**：`activated_accounts` 记录已激活账号集合——换号需重新激活。
3. **VIP 分层**：`vip_list.json` 给出 VIP uid 名单，`isVipUid(uid)` 决定功能放行；名单服务端可控，可随时增删。

## 5. 安全边界：破解的"真难点"

要正确评估此系统的强度，必须先分清**两层校验**：

1. **服务端校验**（Cloudflare Workers）：激活码是否有效、是否被绑定。此逻辑在服务器上，**客户端看不到、改不到**。
2. **客户端本地状态**（MMKV `kevin_prefs` 里的 `activation_activated` 等）：只是 UI 展示层缓存。

结论性的边界：

- **改客户端 / 改本地存储**：最多让 UI 显示"已激活"，**拿不到服务端的真实授权**——因为每次进入主页都会重新 `checkVerification`，与云端再次确认；服务端记录的是激活码↔uid 绑定，客户端自欺无效。
- **伪造响应**：需要让客户端信任一个假"ok"响应（重放/中间人/补丁）。由于校验入口在服务端，且激活码必须先在服务端数据库"存在且未绑定"，单纯伪造回包不等于获得授权。
- **真正的攻击面在服务端**：Cloudflare Workers 代码、激活码生成/校验逻辑、`vip_list.json` 的更新渠道——这些都在作者侧，不在 APK 里。静态逆向 APK 能还原的只是**客户端协议**。

因此，对该系统而言，"破解"的难度集中在**云端服务端实现**，而非 APK 本身。这是把授权逻辑放上 serverless 平台的直接收益。

## 6. 结论

- 云端本质是**服务端校验的授权系统**：激活码有效性、uid 绑定、VIP 名单全部由作者侧控制。
- APK 能逆向出的只是**客户端协议**（POST `/activate`、GET `/vip_list.json`、MMKV 落盘），不含任何可复用的密钥或自校验逻辑。
- 对该系统而言，绕过授权的有效途径全部指向**服务端**（Workers 代码、激活码库、名单源），而这些不在 APK 交付物内。
- 从研究角度：这套设计的强点是"授权逻辑上云"，弱点是**协议层未签名/未绑定设备**。若作者在服务端补齐签名 + 限流 + 设备绑定，客户端侧几乎无可乘之机。
