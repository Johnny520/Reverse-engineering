# 挖红薯呀 — 破解云端（授权验证机制分析与绕过思路）

> 分析对象：`挖红薯呀 3.0_3.0.1`（包名 `top.anjao2024.xp1whs`）
> 本文配套《云端接口调用逻辑.md》，聚焦「激活码」授权验证体系（`verify.php`）的签名协议、密钥与绕过点。
> 混淆类归属：授权验证全部在 `p000/n90.java`（单例 `n90.f4211a`），激活流程编排在 `p000/kf1.java`（Xposed 模块主入口，继承 `XposedModule`）。

---

## 1. 授权验证机制总览

激活流程（`kf1.java`）在本地授权满足条件后，用「小红书 ID」+「授权码」向作者服务器发起 POST 验签：

```
激活流程 kf1.java:1032
  └─ new Thread(RunnableC0084ca) → kf1.m1832Y(kf1.java:1056)
       └─ n90.m2675O(context, 授权码, 小红书ID)      ← 入口（n90.java:339）
            ├─ 1. 按授权码前缀选接口 + HMAC 密钥
            ├─ 2. 构造请求体 key=…&redbook_id=…&sign=Hex(HMAC-SHA256(key=…&redbook_id=…, 密钥))
            ├─ 3. POST 到 verify.php（n90.m2649M，n90.java:160）
            ├─ 4. 用同一密钥二次验签服务器响应中的 sign（防中间人篡改响应）
            ├─ 5. code==200 → 写本地 SharedPreferences("xp1_license")
            └─ 失败 → kf1.m1833Z 清空本地授权 + 弹「激活失败」
```

**核心判断（重要）**：授权是否有效，最终由**服务器** `code==200` 判定。客户端不持有服务器私钥，仅持有 HMAC 密钥——HMAC 密钥是**对称的**，直接硬编码在 APK 里，逆向即可完整还原签名算法。这决定了「破解」可行性的边界（见 §5）。

## 2. 签名协议完整还原

### 2.1 请求体（`n90.java:354-355`）

```
key=<授权码>&redbook_id=<小红书ID>&sign=<sign>
sign = URLEncode( Hex( HmacSHA256( "key=<授权码>&redbook_id=<小红书ID>", 密钥 ) ) )
```

- HMAC 实现：`n90.java:124` `m2647K`，`Mac.getInstance("HmacSHA256")`，输出逐字节 `%02x` 转小写 hex。
- 注意请求体里 `key`/`redbook_id` 均未 URLEncode，只有 `sign` 做了 `URLEncoder.encode`。

### 2.2 两套接口与密钥（`n90.java:344-355`）

| 授权码前缀 | 接口 URL | HMAC 密钥（base64 明文） | 常量方法 |
|-----------|---------|--------------------------|---------|
| `WHS-X-` | `https://anjao2024.top/auth/verify.php` | `lQF7RGJwJwSsUKsQu8nOWBaM3dXywnzP/3BAxa1EFu0=` | `m2663m` / `m2670t` |
| `WHS-Y-` | `https://anjao2024.top/auth_public/verify.php` | `XkT+heMGMAIP02ryj66hi7Cpwhar5Oi1z7yYcthAhXL6JSbn` | `m2638A` / `m2669s` |
| 其他 | — | —（直接拒绝） | `invalid_key_format` |

前缀判定：`r41.m3382S(key, "WHS-Y-")` 先判；不满足再判 `WHS-X-`。

### 2.3 响应二次验签（`n90.java:194-219`）

服务器响应 JSON 除 `sign` 外的字段，客户端同样做一次 HMAC 校验，防止代理篡改响应：

```
1. sign = response["sign"]；为空 → 返回 "sign_missing"
2. response.remove("sign")
3. 剩余字段按键名升序排序，序列化为 key=URLEncode(value)，& 连接
   （序列化器：r01.m3372x + C0553oj，值走 URLEncoder）
4. 用同一密钥 HMAC 比对，不一致 → 返回 "sign_verify_failed"
5. code==200 → 成功（C0504a(true)）
```

### 2.4 响应对象 `n90.C0504a`

- `f4224a`（boolean）：是否通过（`m2683e()`）
- `f4225b`（String）：失败原因（`sign_missing` / `sign_verify_failed` / `network_error` / `invalid_key_format` / 服务器 `msg`）

## 3. 本地授权状态（SharedPreferences）

验证成功后写入（`n90.java:356-363`），文件 `xp1_license`：

| key | 值 | 用途 |
|-----|-----|------|
| `uid` | 小红书 ID | 绑定设备 |
| `ok` | `true` | 授权标记 |
| `akey` | 授权码 | 回显 |

本地授权检查 `n90.m2674J(context, 小红书ID)`（`n90.java:329`）：

```java
String uid = prefs.getString("uid", null);
return uid != null && uid.equals(小红书ID) && prefs.getBoolean("ok", false);
```

清空授权：`n90.m2676v`（`n90.java:369`）→ `prefs.edit().clear().commit()`。
读取已存授权码：`n90.m2677x`；授权类型标记：`n90.m2678y`（`WHS-Y-` 开头 → `"Y"`，否则 `"X"`）。

## 4. 关键 Hook 点（Xposed/LSPosed 视角）

模块自身是 `libxposed` 模块（`kf1 extends XposedModule`），但激活与授权 UI 跑在宿主（小红书）进程或模块自身进程中，Hook 目标如下：

| 目标 | 位置 | Hook 效果 |
|------|------|-----------|
| `n90.m2675O(Context, String, String)` | `n90.java:339` | 直接构造成功结果 `C0504a(true, null)` 返回，跳过一切网络请求 |
| `n90.m2674J(Context, String)` | `n90.java:329` | 强制返回 `true`，本地授权检查永远通过 |
| `n90.m2649M(String, String, String)` | `n90.java:160` | 截断网络层，返回伪造成功响应（需构造合法 `sign`，密钥已知） |
| `kf1.m1833Z(C0504a, ...)` | `kf1.java:1063` | 吞掉「激活失败」后续清理逻辑 |
| `kf1.m1832Y(...)` | `kf1.java:1056` | 跳过授权验证线程的发起 |

> 注意：Hook 需同时覆盖「激活 UI 路径」与「每次启动的本地校验路径」，否则会出现「界面显示已激活但功能校验仍走 `m2674J`」的割裂。

## 5. 破解可行性分析（边界说明）

**可以本地还原/伪造的部分（客户端持有对称密钥）：**
- 签名算法与密钥完全在 APK 内，可离线复现 `sign` 计算（§2.1）。
- 本地 `xp1_license` 状态可注入/伪造，`m2674J` 可被 Hook 覆盖。
- 若只面向「本地功能开关」，Hook `m2674J` / `m2675O` 即可稳定放行。

**无法单纯靠客户端完成的部分（服务器强校验）：**
- 授权码有效性由服务器判定（`code==200`），本地没有授权码白名单。
- 伪造服务器响应需自行生成响应 `sign`（密钥已知，理论可行），但**拦截/改包属于网络中间人行为**，且若服务器端存在会话/绑定态校验，改包会被会话失效兜底拦截。
- 通过激活码「本地算 sign」无法生成合法授权码——`key` 必须是被服务器接受的激活码，密钥只能用于签名验证，不能用于制造授权。

**结论**：该模块的授权防线实质上是「服务器白名单 + 客户端对称签名的响应校验」。纯离线破解的有效路径是 **Hook 客户端校验函数 / 注入本地授权状态**；网络层的响应伪造虽然签名可算，但受服务器绑定态约束且属改包行为，不构成稳定方案。
