## 0. 结论先行

**本模块不存在「云端拉取捐赠名单」的接口。** 捐赠/致谢名单（12 个昵称）、开发帮助者名单、打赏二维码全部**硬编码在 APK 源码字面量与本地资源**中，运行时不访问任何云端地址拉取名单。

模块真正访问的云端接口只有 **3 个**，均指向作者自己的服务器 `anjao2024.top`：

## 1. 接口一：在线公告 `notice.php`

### 1.1 请求

- 请求地址：`https://anjao2024.top/auth_notice/notice.php`（`hk0.java:303`，方法 `m1366t`）
- 请求方式：GET
- 连接/读超时：各 5000ms
- 防并发：静态布尔 `hk0.f2280f`，为 `true` 时忽略新请求

### 1.2 响应结构

```json
{
  "code": 200,                     // optInt("code")，非 200 则丢弃
  "data": {
    "enabled": true,               // optBoolean("enabled")，false 则清理本地记录
    "title": "通知",               // optString("title")
    "content": "...",              // optString("content")
    "button_text": "我知道了",      // optString("button_text")
    "button_url": ""               // optString("button_url")
  }
}
```

### 1.3 本地去重与弹窗

- 以 `(title + content).hashCode()` 为去重键，存入 `SharedPreferences("notice_prefs")` 的 key `last_notice_ver`（`hk0.java:296`）。
- hashCode 与上次相同 → 不再弹窗；不同 → 更新并弹 `AlertDialog`。
- 弹窗按钮带 `button_url` 时，点击通过浏览器打开（`hk0.java:264` `m1345Q`，自动补 `https://` 前缀）。
- 公告关闭后公告记录保留，`enabled=false` 时删除记录。

### 1.4 两个拉取入口

| 方法 | 签名 | 行为 |
|------|------|------|
| `hk0.m1368w(Context)` | 静默拉取 | 失败仅置 `f2280f=false`，不回调 |
| `hk0.m1370z(回调, Context)` | 带回调拉取 | 成功/失败通过 `RunnableC0824v1` 把结果码回传 |

对外触发方法：
- `hk0.m1371v(Context)`：直接起 `Thread` 静默拉取。
- `hk0.m1372y(Context, 回调)`：带回调版本，供 UI 直接检查公告。

### 1.5 触发时机（调用点）

| 调用点 | 场景 |
|--------|------|
| `kf1.java:1027`（`m1885z0` 后） | 激活流程：同意使用协议后自动静默拉公告 |
| `kf1.java:1040 / 1049`（`m1830W` / `m1831X`） | 激活对话框回调后再次静默拉公告 |

## 2. 接口二：版本校验 `version_check.php`

### 2.1 请求

- 请求地址（`wb1.java:195` `m4963r`）：
  ```
  https://anjao2024.top/auth_notice/version_check.php?module_version=30121&app_version=<应用版本号>
  ```
- 请求方式：GET，超时各 5000ms
- `module_version` 为**模块自身版本号，硬编码字符串 `"30121"`**（`wb1.java:243`）
- `app_version` 为宿主应用（小红书）版本号，由调用方传入

### 2.2 响应结构

```json
{
  "code": 200,
  "data": {
    "need_update": false,             // optBoolean，true 弹更新框
    "min_module_version": "",         // 模块最低版本，> 30121 则强制更新
    "min_app_version": "",            // 应用最低版本
    "update_info": {                  // need_update 为 true 时读取
      "title": "版本过低",
      "content": "请更新模块到最新版本"
    },
    "update_title": "",               // update_info 缺失时的兜底
    "update_content": ""
  }
}
```

### 2.3 逻辑要点

- 若 `data` 中**没有** `need_update` 字段（旧服务器协议），则退化为比较 `min_module_version` / `min_app_version`，任一不满足即视为需要更新（`wb1.java:303-316`）。
- 需要更新 → 主线程弹更新对话框（`wb1.java:321-336`）。
- 请求失败 / `code != 200` / 响应空 → 静默跳过（`wb1.java:270-296`）。

### 2.4 触发时机

| 调用点 | 场景 |
|--------|------|
| `kf1.java:746` | 激活流程中，本地授权状态满足（`DialogC0076c2` 判定通过）后，经 `wb1.m4974s(activity, appVersion, 回调)` 启动线程拉取 |

## 3. 接口三：授权验证 `verify.php`

这是模块「激活码」体系的云端核心，签名要求最严格，详见配套文档《破解云端-授权验证分析.md》。

### 3.1 请求

- 请求地址（`n90.java:247/254`）：
  - 正式：`https://anjao2024.top/auth/verify.php`
  - 公开：`https://anjao2024.top/auth_public/verify.php`
- 请求方式：POST，`Content-Type: application/x-www-form-urlencoded`
- 请求体（`n90.java:354`）：
  ```
  key=<授权码>&redbook_id=<小红书ID/设备标识>&sign=<HMAC-SHA256 hex>
  ```
- 超时：各 8000ms

### 3.2 两套密钥（由授权码前缀决定）

| 授权码前缀 | 接口 | HMAC 密钥 |
|-----------|------|-----------|
| `WHS-X-` | `auth/verify.php`（正式） | `lQF7RGJwJwSsUKsQu8nOWBaM3dXywnzP/3BAxa1EFu0=` |
| `WHS-Y-` | `auth_public/verify.php`（公开） | `XkT+heMGMAIP02ryj66hi7Cpwhar5Oi1z7yYcthAhXL6JSbn` |
| 其他 | — | 返回 `invalid_key_format` |

### 3.3 签名算法（`n90.java:124` `m2647K`）

```
sign = Hex( HMAC-SHA256( key=「授权码」&redbook_id=「ID」, 该前缀对应密钥 ) )
```

即对 `key=...&redbook_id=...` 字符串，用上面表格中的密钥做 HmacSHA256，结果转小写 hex。

### 3.4 响应与客户端二次验签（`n90.java:194-219`）

```json
{
  "sign": "<服务器对响应体做的 HMAC>",
  "code": 200,
  "msg": "..."
}
```

客户端拿到响应后：
1. 取 `sign`，为空 → 返回 `sign_missing`；
2. 从 JSON 中**删除** `sign` 字段；
3. 剩余字段按键名排序，以 `key=value`（value 做 `URLEncoder`）形式用 `&` 连接；
4. 用**同一把 HMAC 密钥**对该串重新算 HMAC，与响应 `sign` 比对 → 不一致返回 `sign_verify_failed`；
5. `code == 200` → 验证通过。

### 3.5 验证通过后的本地状态（`n90.java:356-363`）

写入 `SharedPreferences("xp1_license")`：

| key | 值 |
|-----|-----|
| `uid` | `redbook_id`（`n90.java:359`） |
| `ok` | `true`（`n90.java:360`） |
| `akey` | 授权码（`n90.java:361`） |

之后每次「本地授权检查」`n90.m2674J(context, redbookId)`（`n90.java:329`）只需满足：`prefs.getString("uid").equals(redbookId) && prefs.getBoolean("ok")`。

### 3.6 触发时机（完整链路）

```
kf1.java:1028-1032  激活流程（已存授权码时）
  └─ new Thread(new RunnableC0084ca(context, 授权码, 小红书ID, kf1, activity))
       └─ RunnableC0084ca.run()  (case 2)  →  kf1.m1832Y(context, 授权码, ID, ...)
            └─ n90.m2675O(context, 授权码, ID)          ← 真正发起 POST
                 ├─ 构建 key/redbook_id/sign → m2649M(url, body, 密钥)
                 └─ 成功 → 写 SharedPreferences("xp1_license")
```

验证失败处理：`kf1.m1833Z`（`kf1.java:1063`）→ `n90.m2676v` 清空 `xp1_license` 全部字段 + 弹「激活失败」提示。
