## 一、这是什么

这是一个 **Xposed 模块**（官方名"AI抖音"），使用 LibXposed 框架，注入抖音宿主进程（`com.ss.android.ugc.aweme` 系列）后实现：

- 作品/评论/私信批量下载、去水印
- AI 语音合成（TTS）、AI 互动
- 评论区增强（表情、口令、分享）
- 个人主页作品快速到底、批量操作
- 数据备份/恢复（WebDAV）、"插眼"数据（收藏夹 `ward_items` 数据库）
- 各种 UI 增强（时间显示、自动连播、续火等）

## 四、原生库 `libnative.so` 分析

### 基本信息
- 路径：`lib/arm64-v8a/libnative.so`（8.2 MB，Rust 编写，rustc 1.98.0-nightly）
- **特点**：带有自定义段 **`enc_text`（362 KB）**，JNI_OnLoad 和约 40 个核心函数都加密存储

### 加密机制
| 内容 | 说明 |
|---|---|
| 构造函数 | `0x61b140`（init_array 入口），运行时把 `enc_text` 段逐字节 XOR 解密 |
| 加密算法 | 循环：`data[i] ^= key[i]`，密钥来自 `.rodata` 加密池 `0xb4370` |
| JNI_OnLoad | 位于 `enc_text` 段起始 `0x74e228`，**解密后才能执行** |
| 字符串池 | `0xb4370` 整块加密，运行时解密到 `.bss` |
| 防分析 | 符号名恶搞：`bu_yao_tou_kan_zai_kan_da_ni_pi_pi`（"不要偷看再看打你皮皮"） |

### 解密结果
- ✅ **`enc_text` 段已通过 unicorn 模拟执行构造函数成功解密**，还原为有效 ARM64 指令（`stp x29,x30` 函数序言）
- ✅ 解密产物：`libnative_decrypted.so` / `enc_text_emulated.bin`
- 解密后包含约 40 个函数、90650 条指令
- 原生层负责：JNI 方法注册、部分配置读写、黑/白名单判断等

## 六、加载限制机制（"过来多长时间就不加载"）

### 结论：这是**版本适配机制**，不是单纯的时间限制

模块通过 `assets/versions.json` 维护**抖音系 App 的适配版本清单**：

```json
[
  {"id":"com.ss.android.ugc.aweme.hubble","name":"AI抖音","versionCode":390801,"updateVersionCode":"39809900"},
  {"id":"com.ss.android.ugc.aweme","name":"抖音","versionCode":390801,"updateVersionCode":"39809900"},
  {"id":"com.ss.android.ugc.aweme","name":"抖音","versionCode":390900,"updateVersionCode":"39900100"},
  ... 共 13 条
]
```

### 工作流程
1. 模块启动时扫描**设备上已安装的抖音系 App**（`GET_INSTALLED_APPS` 权限）
2. 用 `AdaptedVersion`（`packageName` + `updateVersionCode`）比对 `versions.json`
3. 如果**当前安装的抖音版本号不在适配列表** → **模块不加载**（显示"未激活"/"未发现适配应用"）
4. 只有版本匹配才显示"已激活"，注入抖音进程

### 相关代码
| 位置 | 作用 |
|---|---|
| `MainActivity.java` 的 `AdaptedVersion` 内部类 | 版本比对数据 |
| `yyds/C2001.java` | 加载/解析适配版本列表 |
| `yyds/C2268.java`、`yyds/C0178.java` | 版本适配实体 |
| `MainActivity.java` 授权流程 | "扫描适配应用失败" / "未发现适配应用" / "已激活" / "未激活" / "去授权" / "重新授权" |

### 关键字符串
```
已激活 / 未激活 / 去授权 / 重新授权
用于识别当前设备已安装的适配应用，并判断版本是否可用。
暂时无法判断当前设备已安装的适配应用。授权后可以重新读取列表。
扫描适配应用失败 / 未发现适配应用
```

## 七、黑名单 / 白名单 UID

### 存储方式（重要发现）

经全面检索，这些 UID **不以明文形式存在于任何 APK 文件中**：
- ❌ 不在 DEX / smali 源码
- ❌ 不在解密字符串表（`decrypted_strings.tsv`）
- ❌ 不在解密后的 `libnative.so` 明文段
- ❌ 不在资源 / assets / 数据库

**结论**：黑名单 UID 由 `libnative.so` 的**加密字符串池**（`.rodata` 0xb4370 区域，运行时解密）在 JNI 初始化时构造，或由远端服务器下发。这正是原生层 `enc_text` 加密 + 字符串池加密的双重保护所在。

### 相关数据结构（Java 侧可见）
- 数据库 `ward_items` 表含 `authorUid` 字段（收藏夹按作者 UID 分类）
- 关键词：`authorUid`、`secUid`、`uid`、`主播 UID`
- hook 点：`UserStats(authorUid=...)` 用户统计

## 八、字符串加密解密机制（已破解）

### Java 层（`AbstractC2328.m4341`）
```
加密表：f11475（95 段，共 409546 字符，日文片假名混淆）
算法：64 位混淆哈希 + 按索引逐字符 XOR
```
**已完全破解**，7775 个加密字符串全部还原为明文，见 `decrypted_strings.tsv`。

### Native 层（`enc_text` + 字符串池）
```
enc_text 段：构造函数 0x61b140 XOR 解密
字符串池：.rodata 0xb4370，运行时解密到 .bss
```
**enc_text 已解密**（见 `libnative_decrypted.so`）。
